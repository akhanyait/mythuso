# Adversary register — device fleet and multi-tenant GilbertOne

Companion to `docs/security/THREAT-MODEL.md`. Ten adversaries, named verbatim from Module 10 of the
founder's "Control Tower & GilbertOne Commercialization" plan. Each row is read against what is
actually built on 23 September 2026, not against the device-pairing/trust or multi-tenancy modules
this plan scopes but has not started. "Not applicable" below means exactly that — not a hedge, a
finding: the thing this adversary would attack does not exist yet, so there is nothing to defend.

Status vocabulary follows `docs/PRIVACY-AND-SECURITY.md`: **built** (code that runs, with a test),
**proposed** (designed in a contract or a document, nothing enforces it), **not-yet-started** (no
design exists beyond the adversary's name in the founder's plan).

| Adversary | What they can do today | Control that answers them once device pairing/trust lands | Status |
|---|---|---|---|
| **Malicious insider** | Somebody with database or environment access on the server already reads everything the identity service holds — that is unchanged by device or tenant work and is the same risk `docs/governance/DPIA-DRAFT.md` records as R-2 and R-3. No device data flows through any service today (`packages/catalog/devices.json` "whereValuesLive": a reading's value never reaches the Devices engine at all), so there is no device-specific insider surface yet — an insider today can see that a reading reference exists, never what it measured. | Device data, once it flows, goes through the same chokepoint clinical data already does: `apps/api/src/protection/gate.ts` (capability, standing, purpose, before plaintext exists) and the HMAC-keyed audit chain in `audit.ts`. That does not stop root — `bootstrap.ts`'s own comment says so — and the two things that would close the remaining gap for an insider with database access are unchanged by device work: KMS/HSM split-knowledge key custody, and publishing the audit chain head somewhere MyThuso does not control (`witness.ts`: "nothing in this file publishes anything," by design, because that needs a second organisation). | **Partly built** for the mechanism (gate + audit chain exist and would cover device data the same way); **not-yet-started** for the two measures that answer an insider with root, which DPIA §9 lists as blocked on hosting and key-custody decisions no device work resolves. |
| **Compromised device** | No route accepts a device-originated write carrying its own credential. The only path a reading takes into the system is through a *capturer* — a vetted nurse or patient — using their own standing, via `POST /v1/devices/readings@2`; the device itself proves nothing and holds no key. A compromised instrument today can produce a bad reading, but the reading is decided on the capturer's vetting, not the device's identity, because the device has no identity to compromise. | Device binding — a per-device credential distinct from the capturer's, so a route can refuse a reading whose device key does not match its claimed serial. `docs/governance/DPIA-DRAFT.md` §9 lists "Device binding" by name: "A device id on a request is a claim," blocked on "A key per device." | **Not-yet-started.** No design for a device credential exists anywhere in the catalog or the codebase. |
| **Compromised tenant key** | No tenant key exists. `docs/COMMERCIAL-AND-CONTROL-TOWER-SCOPE.md`'s own audit of the founder's note found that `gilbertone-api-keys.json` and `gilbertone-api-versioning.json` — the two files a scoped-per-institution key would live in — are not in the tree, and `apps/assistant-api/src/server.ts` has no notion of a tenant at all (its one mention of "tenant" is a code comment about a co-hosted, unrelated website sharing the same VPS). There is nothing to compromise because nothing has been minted. | Scoped API keys per institution with server-side tenant isolation — `docs/COMMERCIAL-AND-CONTROL-TOWER-SCOPE.md` §2, "New engine modules for commercialization," item 1 ("Multi-tenancy and tenant isolation — one deployment, many hospitals, no cross-tenant read"). Revocation and rotation of a single tenant's key without touching another tenant's is the property that answers this adversary specifically. | **Not-yet-started.** Named as scoped work in the commercial plan; no contract, no route, no key format exists. |
| **Spoofed device** | A device is registered by an operator typing a serial number and a class (`certified`, `consumer`, `simulator`) into `POST /v1/devices/registry@2`. Nothing about that registration is cryptographically tied to a real instrument — the "certified" class that lets a reading carry clinical weight (`packages/catalog/devices.json` `clinicalWeight.requires`) is a label an operator asserts, not a proof the system checks. So today, "spoofing" a certified device costs nothing more than an operator (or anyone with operator-role access) typing the wrong class into a form — there is no instrument to impersonate over a wire, because no wire exists yet. | The real-device allowlist becoming a cryptographic identity rather than a label: a registered device's serial paired with a key, checked on every reading rather than trusted from the registry row. `docs/COMMERCIAL-AND-CONTROL-TOWER-SCOPE.md` records the allowlist at 0 devices against a DPIA marked "not-done" for exactly this class of work. | **Not-yet-started.** The allowlist concept exists in the contract (`deviceClasses`); the cryptographic verification that would make it resist spoofing does not. |
| **Replayed reading** | No route ingests a device reading's value at all, so there is no value to replay in the clinical sense. A precedent for replay detection does exist in the codebase, but for a different surface: `apps/api/src/capture/index.ts` uses the entry's own id as an idempotency key for a nurse's offline batch sync, and a repeat is recorded in the audit chain as `capture.replayed` rather than silently reprocessed. That mechanism has never been extended to a device's own telemetry — there is no route where a device, rather than a human capturer, submits a reading with a nonce or sequence number the server checks. | The same idempotency-key pattern already proven in `capture/index.ts`, extended to device-originated submissions once a real device gateway exists — plus a monotonic counter or nonce per device, since a stolen reading replayed a day later needs more than an id match to catch. `docs/COMMERCIAL-AND-CONTROL-TOWER-SCOPE.md` §3 names the device gateway ("MQTT / device-gateway ingestion") this would sit in front of. | **Proposed** in the sense that a working pattern exists one module over; **not-yet-started** for device telemetry specifically — nothing applies it there today. |
| **Rogue BLE advertiser** | No attack surface exists. `apps/web/src/features/KitCapture.tsx` states this outright in its own top comment: "There is no `navigator.bluetooth` call anywhere in this repository and no native bridge to one." Neither native app declares a Bluetooth permission — `apps/android/app/src/main/AndroidManifest.xml` requests only `RECORD_AUDIO` and `INTERNET`, no `BLUETOOTH_SCAN` or `BLUETOOTH_CONNECT`; the iOS project has no `Info.plist` file and no `INFOPLIST_KEY_NSBluetooth*` build setting anywhere in `apps/ios/MyThuso.xcodeproj/project.pbxproj` — because neither app has ever asked for one. A rogue advertiser has nothing listening for it on any MyThuso device. | Real BLE pairing, once built, requiring an explicit user-confirmed pairing action (never auto-connect to an advertised device), and checking any paired device's identifier against the real-device allowlist before a reading from it is accepted. This is downstream of device binding, above — a BLE control without a device credential to check the connection against is decoration. | **Not applicable today** — there is nothing to defend, stated as a finding rather than a gap. **Not-yet-started** once real BLE pairing exists, since no pairing-confirmation or allowlist-check design exists yet either. |
| **Stolen field device with buffered data** | As designed, a Thuso Kit instrument holds nothing to steal: `packages/catalog/devices.json`'s `whereValuesLive` is explicit that a reading's value never reaches the instrument's own record — the capturer writes it straight to the Health Passport under their own grant, and the instrument is asked for nothing afterward. A *nurse's phone*, carrying the offline capture queue in `apps/api/src/capture`, is a more honest match for this adversary today, and it already has a partial answer: cleartext storage is disabled on Android (`docs/PRIVACY-AND-SECURITY.md`, "Encryption" row), and nothing filed through capture is clinical content until it clears the gate. Losing a *kit* is modelled separately — `packages/catalog/devices.json` `kits.states` includes `lost`, with reasons (`stolen`, `left-behind`, `destroyed`) and an append-only audit — but that is deposit and inventory accounting, not a data-buffer concern, because there is no buffer on the instrument to account for. | For a real instrument that does eventually buffer readings locally (a glucometer or a BP cuff holding unsynced results between visits, which is plausible hardware behaviour this contract does not yet model): on-device encryption of anything buffered, and a lost-kit report (`POST /v1/devices/kits/{kitRef}/loss@2`) that deregisters the instrument's credential rather than only recording that it went missing. That linkage — a kit marked lost automatically revoking its instruments' standing in the allowlist — is not specified anywhere in the current contract. | **Partly built** for the adjacent nurse-phone case (Android cleartext disabled, capture queue gated); **not-yet-started** for an instrument's own local buffer, because the contract does not yet model one existing, and the lost-kit-to-revoked-credential linkage above is an unaddressed gap even at the design level. |
| **External attacker** | Nothing device-related is network-reachable. The two "doors" `packages/catalog/devices.json` names for an external feed — `device-reading` and `wearable-sync` in `packages/catalog/feeds.json` — refuse every payload by contract; GilbertOne's own service binds to `127.0.0.1:8791` behind nginx's `location /assistant/`, installed dark in production; and the devices engine itself runs only inside the development simulator in `packages/engines/src/runtime`, never exposed. An external attacker aimed at "a device" has no live endpoint to reach. | Mutual TLS and per-device or per-gateway credentials in front of whatever device gateway is eventually built (`docs/COMMERCIAL-AND-CONTROL-TOWER-SCOPE.md` §3's proposed MQTT/device-gateway path), matching the same gap `docs/governance/DPIA-DRAFT.md` §9 already records for the Passport: "OIDC and mutual TLS in front of the Passport gateway — Nothing authenticates a requester beyond a signed grant." | **Not-yet-started.** Today's answer is structural (nothing switched on) rather than a control anyone built; the moment a device gateway is switched on, this row needs its own row-specific control, because "nothing is reachable" stops being true on day one of that build. |
| **Curious admin** | For identity and vetting data, this is already answered: `apps/api/src/protection/gate.ts` resolves capability, standing and purpose on every single read, and every access — including a refusal — is written to the hash-chained audit log before plaintext exists. Device data does not go through that gate at all. The devices contract's v2 routes do declare callers (`operator`, `nurse`, `patient`, `admin`, per `packages/catalog/apis/devices.json`), but the engine that actually answers those routes today, `packages/engines/src/devices`, runs on a development runtime (`packages/engines/src/runtime`: a simulated clock, an in-process event bus) that never imports `apps/api/src/protection` — confirmed by grep, nothing under `packages/engines/src` references the gate. So an admin curious about device data in the current build is constrained only by the mock/dev engine's own fixture-level refusals, not by the hardened chokepoint clinical and identity data already have. | Routing device reads through the same gate pattern once a real device backend exists — capability and purpose checked per read, every view audited — rather than leaving device data as the one contract whose enforcement lives entirely in a development simulator. | **Proposed** at the contract level (callers are declared per route, with refusal sentences); **not-yet-started** for real enforcement, since the only thing currently answering these routes is dev-only. |
| **Lost field device** | Closest to being answered of the ten. `packages/catalog/devices.json` `kits.states` includes `lost`, with named reasons and an append-only per-kit audit (`kits.auditMeans`: "Every issue, return and loss is a row added to the kit's audit with who, when and why. Nothing in it is edited or removed"). A loss charges nobody (`kits.lossNeverCharges`) and is distinct from a device *recall* (`marks.recalled`), which is the mechanism that would actually stop a lost instrument's future readings from carrying clinical weight. The gap: nothing in the contract ties "this kit was reported lost" to "therefore recall the instruments it contained." Reporting a kit lost today records the loss; it does not, by itself, revoke anything. | Wiring `POST /v1/devices/kits/{kitRef}/loss@2` to automatically recall every instrument registered against that kit, so a lost field device stops being trustable the moment it is reported rather than only when someone separately remembers to recall it. This is a contract change (a new rule in `devices.json`, not new infrastructure) and is the cheapest of the ten rows to close once somebody decides it. | **Partly built** — the loss-reporting and audit machinery exists and works as designed; **proposed, not built** for the loss-to-recall linkage, which is a one-line gap in the existing contract rather than a missing module. |

## Reading this table honestly

Three adversaries — **rogue BLE advertiser**, **external attacker**, **compromised tenant key** —
have "no current attack surface" as their honest today-answer, because the thing they would attack
(a Bluetooth radio call, a reachable device endpoint, a tenant key) does not exist in this codebase.
That is not a control; it is the absence of a feature. The day any one of those three ships, its row
stops being "not applicable" and starts needing an actual answer, and this table is wrong from that
day until it is revised.

Two adversaries — **curious admin** and **stolen field device with buffered data** — are the ones
where "not-yet-started" understates the gap slightly, because a partial mechanism exists nearby
(the identity/vetting gate; Android's disabled cleartext storage) that has simply never been extended
to cover device data. Extending it is real work, but it is work with a known shape, unlike the
adversaries above where nothing has been designed at all.

The single row most worth a human decision before any device work starts is **compromised device**
and **spoofed device** together: both terminate on the same missing primitive, a per-device
credential (`docs/governance/DPIA-DRAFT.md` §9, "Device binding"), and nothing else in this register
— not the gate, not the audit chain, not the allowlist as currently specified — can answer either
adversary until that credential exists.
